# План доработки адаптивного pipeline DOCX в HTML и PDF

## 1. Цель

Доработать обработку документов так, чтобы GPT Astra 6 могла адаптировать оформление нового DOCX под конкретный PDF-образец, сохраняя исходное содержание, изображения и редактируемую HTML-структуру.

Целевой результат:

```text
DOCX + PDF-образец
        ↓
анализ содержания и визуальной системы
        ↓
design system + editable HTML
        ↓
детерминированный PDF-рендер
        ↓
визуальное сравнение и исправления
        ↓
финальный HTML и PDF
```

## 2. Проблема текущего подхода

Сейчас модель получает заранее определённые компоненты и разрешённые CSS-классы. Это обеспечивает безопасность и стабильность, но ограничивает сходство с конкретным PDF-образцом.

Основные ограничения:

- дизайн-система в значительной степени задана заранее;
- размер страницы и шаблоны страниц не выводятся из эталона автоматически;
- нет отдельного формального слоя `design_system`;
- PDF, созданный после генерации HTML, не сравнивается с эталоном автоматически;
- отсутствует цикл исправлений по визуальным расхождениям;
- модель может получить хорошую интерпретацию стиля, но не точную реконструкцию композиции.

## 3. Целевые принципы

### 3.1. Разделить содержание и оформление

DOCX является источником фактов, текста, структуры и исходных изображений.

PDF-образец является источником визуальной системы:

- формат и ориентация страницы;
- поля и сетка;
- типографика;
- цвета;
- header и footer;
- обложка;
- таблицы;
- предупреждения;
- галереи и фигуры;
- правила разрывов страниц.

Текст и факты из PDF-образца нельзя переносить в новый документ, если они не содержатся в исходном DOCX.

### 3.2. Сохранить контролируемую генерацию

Не разрешать модели произвольный HTML и CSS без ограничений. Вместо этого использовать:

- allowlist безопасных HTML-тегов;
- проверку CSS-свойств и внешних ресурсов;
- обязательные идентификаторы редактируемых блоков;
- запрет JavaScript, iframe и сетевых запросов;
- ограничение на data URI в каноническом HTML;
- проверку JSON-схемы ответа.

При этом визуальные параметры должны быть не фиксированным списком компонентов, а результатом анализа конкретного образца.

## 4. Новая модель ответа Astra

Расширить контракт ответа двумя основными частями:

```json
{
  "design_system": {
    "page": {
      "width": "A5",
      "orientation": "portrait",
      "margins": {
        "top": "18mm",
        "right": "13mm",
        "bottom": "18mm",
        "left": "13mm"
      }
    },
    "colors": {},
    "typography": {},
    "components": {},
    "header_footer": {},
    "page_templates": []
  },
  "document": {
    "html": "...",
    "language": "ru",
    "assets": [],
    "warnings": []
  }
}
```

`design_system` должен быть ограничен валидируемой схемой и разрешённым набором CSS-свойств.

### 4.1. Минимальный состав design system

- размер страницы и ориентация;
- размеры полей;
- базовый шрифт и fallback-шрифты;
- шкала размеров текста;
- межстрочные интервалы;
- основные и вторичные цвета;
- правила заголовков;
- правила списков и таблиц;
- шаблон обложки;
- header/footer и нумерация страниц;
- шаблоны предупреждений и информационных блоков;
- правила размещения изображений;
- правила галерей и overlay-фигур;
- правила разрывов страниц;
- правила оглавления.

## 5. Изменения в pipeline

### Этап 1. Подготовка входных материалов

Для каждой операции передавать Astra:

- полный исходный DOCX;
- визуальный PDF исходного DOCX;
- PDF-образец оформления;
- обзорные PNG-изображения страниц образца;
- изображения, извлечённые из исходного DOCX;
- версию prompt package;
- тему и пользовательские настройки стиля.

Для эталонного PDF дополнительно подготовить:

- размеры страниц;
- количество страниц;
- raster preview каждой страницы или контактный лист;
- при наличии — извлечённые шрифты и изображения;
- хеш входного файла.

### Этап 2. Анализ дизайн-системы

Попросить Astra сначала определить визуальную систему эталона, не смешивая её содержание с содержанием нового DOCX.

На этом этапе модель должна определить:

- формат страницы;
- типовые макеты страниц;
- повторяющиеся блоки;
- правила заголовков;
- цветовую палитру;
- типографику;
- изображения и их размеры;
- характерные элементы бренда;
- правила таблиц и предупреждений.

### Этап 3. Генерация HTML

На основе исходного DOCX и полученной дизайн-системы Astra генерирует:

- канонический редактируемый HTML;
- структурированные ассеты;
- предупреждения о проблемах качества исходного материала;
- список предполагаемых шаблонов страниц;
- при необходимости — предложения по улучшению design system.

HTML должен оставаться семантическим и не зависеть от конкретной пагинации Word.

### Этап 4. Детерминированный PDF-рендер

Сгенерированный HTML рендерится одним и тем же движком, предпочтительно WeasyPrint или Chromium, выбранным по результатам тестов.

Рендерер должен использовать:

- зафиксированный набор шрифтов;
- зафиксированную версию движка;
- одинаковые CSS-параметры;
- локальные изображения и ресурсы;
- запрет внешнего сетевого доступа.

Важно: итоговый PDF строится из HTML, возвращённого Astra. PDF, созданный из исходного DOCX, используется только как входной визуальный источник.

## 6. Визуальное сравнение

Добавить отдельный сервис или модуль `visual_comparator`.

Он должен:

1. Рендерить эталонный PDF и сгенерированный PDF в PNG.
2. Сопоставлять страницы по размеру и номеру.
3. Рассчитывать визуальную разницу.
4. Формировать diff-изображения.
5. Определять крупные зоны расхождений.
6. Передавать Astra компактный отчёт и изображения проблемных страниц.

Минимальные метрики:

- совпадение размера страницы;
- количество страниц;
- средняя pixel difference;
- процент отличающихся пикселей;
- расхождение текстовых блоков;
- расхождение границ таблиц и изображений;
- наличие переполнений и обрезанного текста.

Визуальный diff не должен требовать полного пиксельного совпадения: содержание нового документа отличается от содержания эталона. Сравнивать нужно прежде всего геометрию, композицию, цвета, типографику и повторяющиеся элементы.

## 7. Цикл исправлений

Добавить ограниченный цикл автоматической корректировки:

```text
генерация HTML
   ↓
рендер PDF
   ↓
визуальная проверка
   ↓
если расхождения выше порога — Astra получает diff
   ↓
исправление design system или HTML
   ↓
повторный рендер
```

Рекомендуемые ограничения:

- не более 2–3 итераций;
- отдельная проверка валидности после каждой итерации;
- сохранение каждой версии HTML и PDF;
- остановка при ухудшении результата;
- ручная проверка, если размер страницы или содержание изменились неожиданно.

## 8. Что изменить в prompt package

### 8.1. Убрать избыточную жёсткость

Ослабить требования, которые фиксируют конкретный визуальный стиль для всех документов:

- не требовать один общий набор размеров и отступов для любого образца;
- не ограничивать документ только заранее определённым набором макетов;
- разрешить модели добавлять новые безопасные компоненты в пределах схемы.

### 8.2. Сохранить жёсткие ограничения

Оставить обязательными:

- сохранение всех технических фактов;
- запрет выдумывания содержания;
- разделение исходного DOCX и PDF-образца;
- сохранение изображений в правильном контексте;
- валидную JSON-структуру;
- уникальные `data-block-id`;
- допустимые HTML-теги и CSS-свойства;
- запрет внешних ресурсов и скриптов.

### 8.3. Добавить инструкции по реконструкции

В prompt package явно указать:

- сначала анализировать дизайн-систему, затем генерировать документ;
- использовать PDF как визуальный эталон, а не как источник текста;
- повторять геометрию и визуальную иерархию, если это не противоречит содержанию;
- не переносить страницы механически из исходного DOCX;
- строить итоговую пагинацию через renderer;
- учитывать feedback визуального diff.

## 9. Модель данных и версии

Сохранять для каждой AI-операции:

- `model_id`;
- `prompt_package_version`;
- `design_system_version`;
- хеш DOCX;
- хеш source render PDF;
- хеш style reference PDF;
- версию renderer;
- версию шрифтов;
- параметры рендера;
- список итераций визуальной коррекции;
- метрики визуального сравнения;
- финальные HTML и PDF.

Это позволит воспроизводить результат и понимать, почему оформление изменилось после обновления prompt или renderer.

## 10. Предлагаемые backend-компоненты

Добавить или выделить следующие модули:

- `DesignSystemExtractor` — подготовка и валидация дизайн-системы;
- `DesignSystemSchema` — Pydantic-контракт;
- `SafeCssValidator` — проверка CSS-параметров;
- `VisualComparator` — сравнение PDF-рендеров;
- `PdfPreviewBuilder` — подготовка PNG и контактных листов;
- `DocumentRepairLoop` — ограниченный цикл визуальных исправлений;
- `RenderFingerprint` — фиксация renderer/fonts/settings;
- `DesignSystemRepository` — хранение версий и хешей дизайн-систем.

## 11. Изменения frontend

Пользователю желательно показывать отдельные этапы обработки:

- «Анализируем исходный документ»;
- «Анализируем оформление образца»;
- «Собираем HTML»;
- «Проверяем PDF»;
- «Исправляем визуальные расхождения»;
- «Документ готов».

Для технического режима добавить:

- preview эталона;
- preview результата;
- diff preview;
- выбранный формат страницы;
- версию дизайн-системы;
- предупреждения о расхождениях.

## 12. План реализации

### Фаза 1. Прототип

- Зафиксировать один эталонный PDF и один DOCX.
- Перевести формат страницы на параметры, определяемые из эталона.
- Добавить обзорные изображения страниц эталона в запрос Astra.
- Расширить JSON-контракт блоком `design_system`.
- Сохранить текущую проверку HTML и ассетов.

### Фаза 2. Детерминированный рендер

- Зафиксировать renderer, шрифты и версии зависимостей.
- Добавить автоматический экспорт PDF после генерации HTML.
- Добавить проверку размера страницы, шрифтов, переполнений и отсутствующих изображений.

### Фаза 3. Визуальный diff

- Реализовать рендер PDF в PNG.
- Добавить page-by-page diff.
- Сформировать отчёт с порогами качества.
- Добавить сохранение diff-артефактов.

### Фаза 4. Repair loop

- Передавать Astra diff-изображения и описание расхождений.
- Ограничить количество итераций.
- Сохранять версии каждого результата.
- Останавливать цикл при отсутствии улучшения.

### Фаза 5. Расширение набора шаблонов

- Обложка;
- содержание;
- обычная текстовая страница;
- safety callout;
- технические характеристики;
- таблица обслуживания;
- troubleshooting;
- галерея изображений;
- overlay-иллюстрация;
- форма заказа деталей.

## 13. Критерии приемки

Решение считается готовым, если:

- формат страницы результата совпадает с эталоном;
- header/footer и нумерация воспроизводятся стабильно;
- основные цвета и типографическая иерархия совпадают;
- таблицы не выходят за границы страницы;
- изображения не обрезаются и не теряются;
- предупреждения и ключевые визуальные блоки сохраняют характер эталона;
- HTML остаётся редактируемым;
- все исходные факты и технические значения сохранены;
- повторный запуск с теми же входами даёт сопоставимый результат;
- визуальный diff после допустимого числа итераций ниже согласованного порога;
- все предупреждения и расхождения доступны для ручной проверки.

## 14. Итоговое решение

Не следует полностью отказываться от ограничений и разрешать Astra создавать произвольный HTML/CSS. Следует перенести ограничения с фиксированного внешнего вида на безопасность, структуру и редактируемость.

Визуальную систему нужно получать из конкретного PDF-образца, сохранять как версионируемый `design_system`, применять к HTML и проверять через повторный PDF-рендер и визуальный diff.

Именно это позволит приблизиться к оформлению эталона значительно ближе, чем текущая схема с заранее заданными универсальными компонентами.
